## 1. 结论速览

### 1.1 一句话定位

**这不是一个「材料库」，而是一个「材料选型决策辅助系统」——v0.2 进一步升级为「工程师个人的选型工作台」。**

客户真正的痛点不是「查不到参数」，而是「为了确认一个参数要问一圈人」。材料库只是手段，把分散在人脑和供应商手册里的选型经验，沉淀成可查询、可推荐、可追溯的资产才是目的。

v0.2 的三项新增功能，本质是把系统从「一次性的问答」推进到「有上下文、有过程、有沉淀的工作台」：

- **选型任务 + 待选清单** → 让一次选材从「弹一次结果」变成「一条可回溯的工作线程」
- **回评 + 失败理由入库** → 让系统的推荐质量第一次**可被度量、可被纠偏**（这正是 v0.1 里那几个成功指标的数据来源）
- **数据导出 / 导入** → 让单机积累的知识能被分享，突破「一个人一台电脑」的边界

### 1.2 关于「智能推荐」的核心建议（沿用 v0.1）

**结论：放弃「知识图谱推理」作为一期主线，采用「结构化硬约束过滤 + 本地语义向量召回 + 规则加权排序 + 模板化解释生成」的四段式混合方案。**

理由：在当前数据规模（50-200 条）下，知识图谱是过度设计，且会在冷启动成本、模糊输入处理、数值区间匹配三处卡死。硬约束先行可保证**不满足温度/工艺的材料绝不进推荐列表**，安全性更高。

知识图谱降级为**二期增强项**：当材料规模超过 500 条、跨品类替代关系（如「PA66 可被 PPA 替代」）成为高频需求时再引入。一期只需在数据模型里预留 `material_relation` 表。

### 1.3 技术选型建议（⚠️ 数据库建议较 v0.1 有调整）

| 项         | 建议                                                                            | 核心理由                                                                 |
| ---------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 架构       | 单机本地应用（本地服务 + 浏览器 UI）                                            | 单用户使用，无需内网服务                                                 |
| **后端**   | **Python（FastAPI）**                                                           | 见 1.4                                                                   |
| **数据库** | **SQLite（FTS5 trigram 中文检索 + 内存暴力向量）** ← 较 v0.1 调整              | 见下方「为什么改 SQLite」                                                |
| 向量检索   | 200 条直接内存暴力算余弦即可；如需索引可挂 `sqlite-vec`                          | 数据量太小，向量索引非必需                                               |
| 语义模型   | **bge-small-zh-v1.5（约 100MB）**                                               | 完全本地、CPU 可跑、无需 GPU，单机内存占用 <1GB                          |
| 前端       | React + TypeScript + Ant Design **(需支持类 Chat 会话式交互)**                  | 表格/表单/筛选器组件齐全，v0.2 新增会话流 UI                             |
| 部署       | **Python 打包（可选 PyInstaller 单文件 exe）或本地 venv + 启动脚本**            | 双击即用，**不再需要 Docker**                                            |

#### 为什么数据库从 PostgreSQL 改为 SQLite

v0.1 选 PostgreSQL 的核心论据是「**多用户并发写材料编辑，SQLite 单写者模型会成为瓶颈**」。v0.2 部署形态收窄为**单机单人**后，这条论据直接消失，剩下需要重新评估：

| 需求                      | PostgreSQL 方案             | SQLite 方案                                            | 结论         |
| ------------------------- | --------------------------- | ------------------------------------------------------ | ------------ |
| 多用户并发写              | ✅ 强项                     | ⚠️ 单写者（**单用户下无影响**）                        | SQLite 够用  |
| 中文子串检索              | `pg_trgm`                   | **FTS5 `trigram` 分词器**（对 CJK 子串匹配友好）       | 平手         |
| 结构化/半结构化数据       | `JSONB`                     | `JSON1` 函数                                           | 平手         |
| 向量检索                  | `pgvector` + HNSW 索引      | 200 条内存暴力算 / `sqlite-vec`                        | SQLite 够用  |
| **运维成本**              | 需常驻服务、需 Docker/WSL2  | **零运维，单文件**                                     | **SQLite 胜** |
| **备份 / 导出 / 分享**    | 需 `pg_dump`                | **复制一个 `.db` 文件即可**                            | **SQLite 胜** |
| **Windows 个人电脑友好度** | 需 Docker Desktop（授权/资源） | 纯 Python 进程，可打包 exe                          | **SQLite 胜** |

**建议：一期用 SQLite。** 单用户 + 200 条数据 + Windows 个人电脑 + 需要「导出分享」这几个条件叠加，SQLite 在每个维度都不吃亏，且部署摩擦最小。

**保留迁移口子**：后端必须做**存储层抽象**（Repository 模式），SQL 语句集中在数据访问层，不散落在业务代码里。若二期要变成部门共享（多人访问同一份数据），只需把 SQLite 换成 PostgreSQL，业务逻辑零改动。**这是本方案唯一需要提前付出的架构成本，务必在一期就做。**

### 1.4 后端为什么选 Python 而不是 Go（沿用 v0.1）

你的技术栈是 Java/Go/C++，直觉上倾向 Go。但**这个项目应该选 Python**：

1. **语义模型生态是决定性因素**：本地 embedding 模型，Python 有 `sentence-transformers` / `FlagEmbedding` 一线支持，加载 bge 只要三行；Go 侧无等价成熟方案，只能走 Python 微服务 + Go 主服务的混合架构——既然要起 Python 进程，不如直接全 Python。
2. **SQL 聚合 + 数值区间计算天然契合**：推荐打分核心是「一堆 `BETWEEN` / `CASE WHEN` / 加权求和」，`pandas` / `SQLAlchemy` 写起来远比 Go 手写快。
3. **一期是「需求高频变化」阶段**：50-200 条数据、单用户，Go 的性能优势完全用不上；最大成本是需求变更，Python 迭代速度优势远超 Go 的性能优势。
4. **FastAPI 自带 OpenAPI 文档**：前后端分离下，交互式 API 文档显著提升联调效率。
5. **（v0.2 新增）打包分发友好**：单机场景需要「双击即用」，Python 有 PyInstaller 成熟的单文件打包方案，符合个人电脑部署诉求。

**什么情况下该改用 Go**：二期数据量达数十万级、需对接实时数据流（如产线 MES）、或公司强制统一 Go 技术栈。**建议一期 Python，并保持后端逻辑与 HTTP 层分离，为迁移留口子。**

### 1.5 一期范围（Must）与明确不做（Not Do）

**一期做**

- 材料知识卡：参数结构化存储 + 详情页展示（对齐截图版式）
- 精确检索：按牌号/别名/类别搜索，支持按成本、温度、工艺筛选取交集
- 智能推荐：自然语言场景描述 → 排序推荐列表 + 推荐理由 + 注意事项 + 替代方案
- **选型任务（B5）**：每次推荐询问形成一条类 AI Chat 的会话任务，支持多轮追问、重命名、归档
- **待选材料清单（B6）**：从推荐结果勾选材料进待选，支持自定义备注与标记，随任务持久化
- **回评（C1）**：成功 / 失败 / 不评价；失败理由经语义拆解后作为反面评价入库
- 材料维护：新建 / 编辑（直接生效）/ 变更留痕 + Git 式 diff 对比
- **数据导出（E1）**：导出为 JSON / Excel / Markdown，便于同事间分享材料数据
- **材料包导入（E2）**：导入同事分享的 JSON 材料包，去重合并
- 分类体系维护 + 本地操作日志

**一期明确不做**

- ❌ 角色权限 / 登录鉴权 → 单机单人，不需要
- ❌ 编辑审核流转 → 同上
- ❌ Excel/CSV 批量导入 → 二期（注意：E2 的「材料包导入」是分享闭环，与本条不同）
- ❌ 知识图谱与替代关系推理 → 二期
- ❌ 材料对比视图（多材料参数并排）→ 二期（高性价比，若工期宽裕可提前；待选清单导出已能部分覆盖）
- ❌ 供应商 / 牌号级数据（如 Sabic 5C39H 的实测值）→ 视数据准备情况
- ❌ 移动端适配
- ❌ 与 PLM / ERP 等外部系统集成
- ❌ 多人协同 / 云端同步 → 单机定位，不做

## 2. 需求背景与问题定义

### 2.1 用户画像

| 维度         | 描述                                                                             |
| ------------ | -------------------------------------------------------------------------------- |
| 角色         | 汽车电控工程师（负责 ECU 壳体、连接器、保险丝盒、传感器支架等零件设计）          |
| 专业能力     | 材料学硕士，但刚进入汽车电控零件设计领域                                         |
| 使用时机     | 零件概念设计阶段（选材）、DFM 评审阶段（验证选材）、问题攻关阶段（怀疑材料问题） |
| 当前替代方案 | ① 问材料工程师同事 ② 翻供应商官网/PDF 手册 ③ 翻以往项目 BOM ④ 凭经验猜           |
| 核心诉求     | **快速得到一个「有人替我判断过」的答案，并知道为什么**                           |
| **部署环境** | **自己的个人工作电脑（Windows），本机运行，单用户**                              |

### 2.2 问题陈述

> 电控工程师在零件选材时，缺少一个**权威、即时、可解释**的材料信息与推荐入口，导致每次选材都要发起跨部门/跨供应商的信息获取流程，单次耗时从数十分钟到数天不等，且结果依赖被问者的经验与响应速度，知识无法沉淀。

v0.2 补充：即便系统给出了推荐，**若没有「选型过程」与「结果回评」的载体，经验仍然只停留在一次性的对话里，无法沉淀成可复用、可分享、可度量的资产**。这正是引入选型任务、待选清单与回评闭环的根本动因。

### 2.3 成功衡量指标（v0.2 更新：数据来源已就位）

| 类型 | 指标                                     | 目标值（建议）       | 数据来源                           |
| ---- | ---------------------------------------- | -------------------- | ---------------------------------- |
| 效率 | 单次选材信息获取耗时                     | 从 >30min 降至 <3min | 任务创建 → 首次采用的时间戳差      |
| 效率 | 因选材发起的跨人咨询频次                 | 下降 60%             | 主观调研                           |
| 质量 | 推荐结果采纳率                          | > 40%                | **回评「成功」占比（C1 直接采集）** |
| 质量 | 推荐结果被标注「失败」的比例             | < 15%                | **回评「失败」占比（C1 直接采集）** |
| 使用 | 周活跃使用天数                            | ≥ 3 天/周            | 本机使用日志                       |
| 数据 | 材料条数 / 参数字段完整率                 | 一期 ≥ 50 条，完整率 > 90% | 数据库统计                    |
| **沉淀** | **待选清单被导出/复用的次数**         | 持续增长             | E1 导出日志                        |

> v0.1 时这些指标大多「无法自动采集」，v0.2 的回评功能使**质量类指标第一次有了真实数据源** —— 这是回评功能除「纠偏推荐」外的第二重价值。

| 功能项   | 说明                                                                                                                   |

```
│ 通用塑料 · 别名：PP-H、聚丙烯、均聚PP、PP             │  ← 副标题：别名
```

#### B1 场景描述输入（沿用 v0.1）

**关键设计决策：自然语言输入 + 结构化字段并存的「双通道」输入。**

| 输入方式                     | 说明                                                                                                       | 优先级   |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------- | -------- |
| **主通道：自然语言描述**     | 一个多行文本框，占位提示示例：「我想做一个保险丝座组件，它是一个注塑件，使用场景温度不超过 150°C」         | 主要入口 |
| **辅助通道：结构化解析确认** | 系统从描述中抽取出【零件类型】【加工工艺】【温度上限】【其他约束】，**以可编辑的标签形式回显**，用户可修正 | 必须做   |

**为什么必须做「结构化解析确认」**：这是把「模型的模糊理解」变成「用户确认过的硬约束」的关键一步。只有硬约束确认后，才允许进入过滤环节，从而保证**推荐结果不会因语义理解偏差而漏掉本该推荐的材料**，也不会推荐明显不满足条件的材料。

**解析失败时的降级**：若无法抽取到任何有效约束，提示「没能理解您的需求，请尝试：① 直接选择工艺和温度；② 换个说法」，不返回空列表。

> **v0.2 交互升级**：B1 的输入不再是一个孤立的表单，而是**一条选型任务（B5）的开始** —— 用户输入即创建任务，解析与推荐结果以消息形式进入会话流。

#### B3 推荐理由与注意事项生成（沿用 v0.1）

**结论：一期用「模板 + 槽位填充」生成，不用 LLM 生成自由文本。**

1. 公司不允许外接大模型 → 本地 LLM（7B~14B）需要 GPU，与「单机轻量部署」矛盾
2. 推荐理由的核心是**准确引用库中参数**，模板化生成能保证 100% 不编造数值
3. 推荐理由的结构高度固定（匹配点 → 参数佐证 → 注意事项 → 替代方案），模板足够

**升级路径**：二期若有 GPU 且允许本地 LLM，可将「注意事项的风险提示」部分改为 LLM 生成（输入严格限定为库中字段，输出后做数值校验），提升表达自然度。属增强项，非必需。

#### B4 替代方案推荐（沿用 v0.1）

**逻辑**：推荐列表第 2 名及其后，或「同类别 + 性能相近（温度裕度 ±20%、成本 ±40%）」的材料，标注替代代价（「成本高 30%」「工艺需改为挤出」）。

**注意**：一期不做跨品类的替代关系推理（如「金属件能否用塑料替代」），属知识图谱范畴，留二期。

#### C1 回评与反馈闭环 ★ v0.2 新增

**设计目标：让「这次推荐到底有没有用」这件事被记录下来，失败的原因被沉淀成可影响下一次推荐的数据。**

**1) 回评入口与选项**

回评出现在任务的结果列表底部（以及任务归档前的提示），三种选择：

| 选项         | 说明                                   | 后续动作                                       |
| ------------ | -------------------------------------- | ---------------------------------------------- |
| ✅ **成功**  | 找到了合适材料 / 已采纳                | 记录成功，作为采纳率指标数据                   |
| ❌ **失败**  | 没找到合适的材料 / 推荐不准 / 信息有误 | **必须填写理由**，进入语义拆解流程             |
| ⏭ **不评价** | 用户跳过，不做任何判断                 | 记录为 skipped，不计入成功率也不计入失败率     |

> 用户也可以选择**完全不做任何回评**（关闭界面）。不回评不等于失败，指标计算时分母只统计「已评价」的任务。这是 v0.1 中「用户也可以选择不评价」的落地方式。

**2) 失败理由的采集**

失败时弹出表单：

- **理由文本（必填）**：自由文本，例如「150°C 太高了，实际只有 90°C 的工况，推荐全是高温料」「这家供应商的料我们没用过」
- **问题类型（可选多选）**：① 没有满足硬条件的材料 ② 推荐了不相关的材料 ③ 参数/数值有误 ④ 价格与实际不符 ⑤ 材料信息缺失无法判断 ⑥ 其他
- **指向材料（可选）**：从本次推荐列表中勾选「哪条材料不适用」（可多选，也可不选）

**3) 语义拆解入库（核心机制）**

失败理由文本 → 经语义解析（词典 + 规则 + 向量）→ 结构化：

```
输入：「PBT+GF30 的价格跟实际差太多，我们采购要 40 多，不是 28」
    │
    ▼
拆解结果 {
   涉及材料: ["PBT+GF30"],
   问题维度: ["价格不符"],
   关键词:   ["价格", "采购价", "偏差"],
   置信度:   0.87
}
    │
    ├── 命中具体材料 → 写入 material_negative_feedback（该材料 × 维度 = 价格不符）
    └── 未命中材料（如「都没有合适的」）→ 写入 requirement_gap（需求缺口）
```

**4) 负面反馈的三种消费方式**

| 消费方式         | 说明                                                                                                       |
| ---------------- | ---------------------------------------------------------------------------------------------------------- |
| **详情页提示**   | 材料详情页「历史反馈」区块展示本人记录（A2 已体现），让坑点可见                                              |
| **推荐降权**     | 推荐排序中，对命中负面反馈的材料按权重降分（见 5.2）。**降权计入匹配度修正项，且 hover 时说明「因历史反馈降分」** |
| **知识盲区报告** | 汇总 `requirement_gap` 的高频维度，生成「本周失败分析」：哪些需求反复得不到满足 → 指导补数据 / 补词典        |

**5) 防误伤原则（重要）**

单机场景回评量少，单条负面极易造成误判。因此：

- **单条负面反馈只做「提示」，不直接改变推荐结果**
- 同维度负面达到**阈值（建议 2 次）**后，才在排序中降权，且降权幅度**可配置**
- 降权是「软降权」：材料仍出现在列表中，只是排序靠后，并标注「因历史反馈降分」
- 用户可在设置中**清空/编辑**自己的历史反馈（毕竟是个人数据）

### 4.3 为什么用「区间上下限」而不是单值（沿用 v0.1）

客户截图里参数本身就是区间（「30-40 MPa」「-20~100°C」）。存单值会丢失信息，存字符串无法做数值筛选。**存储为 `min`/`max` 两个数值字段**，是唯一能同时满足「原样展示」和「区间筛选」的方案。

### 4.4 为什么单列 `service_temp_limit`（沿用 v0.1）

推荐逻辑的第一硬约束就是这个字段。截图里「长期使用温度上限」是独立字段（100°C），与「长期使用温度范围」（-20~100°C）并列。单独抽出便于建索引和快速过滤。

### 4.5 为什么新增 `uid` 字段（v0.2 新增）

E1/E2 的分享闭环要求**跨机器识别同一条材料**。自增 `id` 在两台电脑上会重复（各自从 1 开始），无法作为去重依据。因此为每条材料生成**全局唯一 `uid`（UUID）**，导出时携带、导入时据此匹配与去重。这是「同事间分享材料数据」能正常工作的前提。

## 5. 方案设计：智能推荐引擎

### 5.1 四段式推荐流程（沿用 v0.1）

```
用户输入：「我想做一个保险丝座组件，它是一个注塑件，使用场景温度不超过 150°C」
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ 第 1 段：约束抽取（Extraction）                        │
│  规则 + 词典为主，不做开放式语义理解                     │
│  · 零件类型词典匹配 → 「保险丝座组件」→ 电气件/承力+绝缘  │
│  · 工艺词典匹配     → 「注塑件」     → 工艺 = 注塑        │
│  · 数值+单位正则    → 「150°C」      → 温度上限 = 150     │
│  · 其余描述        → 保留为原始文本，供语义检索用          │
│  输出（回显给用户确认）：{零件类型:电气件, 工艺:注塑, 温度:150}│
└─────────────────────────────────────────────────────┘
    │  ← 用户在此处可修正（关键交互）
    ▼
┌─────────────────────────────────────────────────────┐
│ 第 2 段：硬约束过滤（Filtering）★ 安全底线              │
│  纯 SQL WHERE，精确、可审计                            │
│  WHERE service_temp_limit >= 150         -- 温度硬门槛  │
│    AND molding_process 包含 '注塑'        -- 工艺硬门槛  │
│    AND archived = 0                                    │
│  · 结果为空 → 触发降级：放宽温度至 140，并明确提示用户    │
│  · 绝不返回不满足硬约束的材料                            │
└─────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ 第 3 段：语义召回 + 加权排序（Ranking）                 │
│  score = 0.30*温度 + 0.25*语义 + 0.20*成本              │
│        + 0.15*性能 + 0.10*工艺                          │
│        − 反馈降权修正 ← v0.2 新增（见 5.2）             │
│  · 语义分：cosine_sim(bge(用户描述), material.embedding)│
│  · 按 score 降序，取 Top N（默认 5，可调）               │
└─────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ 第 4 段：解释生成（Explanation）                        │
│  模板填充，不调用 LLM                                   │
│  · 匹配点 → 遍历命中的规则，逐条生成「为什么推荐」        │
│  · 关键参数 → 直接从库中取字段值（零编造风险）            │
│  · 注意事项 → 材料 cautions 字段 + 规则触发的风险         │
│  · 替代方案 → 第 2~3 名 + 替代代价说明                  │
```

### 5.2 反馈回流闭环（★ v0.2 新增的核心机制）

v0.1 的推荐流程是**单向**的：输入 → 推荐 → 结束。v0.2 把回评接进来，形成**闭环**：

```
┌──────────────┐
│ ① 智能推荐     │  四段式输出 Top N
└──────┬───────┘
       ▼
┌──────────────┐
│ ② 选型任务     │  多轮追问 + 待选清单 + 自定义备注
└──────┬───────┘
       ▼
┌──────────────┐
│ ③ 回评         │  ✅成功 / ❌失败(必填理由) / ⏭不评价
└──────┬───────┘
       ▼
┌──────────────────────────────────────┐
│ ④ 语义拆解 → 结构化                    │
│    {涉及材料[], 问题维度[], 关键词[], 置信度}│
└──────┬───────────────────────────────┘
       │
       ├── 命中具体材料 → material_negative_feedback
       │      · 材料详情页展示「历史反馈」
       │      · 累计达阈值(建议2次) → ⑤ 推荐降权
       │
       └── 未命中材料   → requirement_gap
              · ⑥ 知识盲区报告 → 指导补数据 / 补词典
       │
       ▼
   回到 ① —— 下一次推荐更准
```

**降权的具体算法（建议）**：

```
feedback_penalty(m) = Σ over dimensions d:
     min(hits(d) / THRESHOLD, 1.0) * DIM_WEIGHT[d] * PENALTY_MAX

其中：
  hits(d)      = 该材料在维度 d 上的有效负面反馈条数
  THRESHOLD    = 2（达到 2 次才生效，单条不计）
  DIM_WEIGHT   = 各维度权重（价格不符 vs 外观瑕疵，对选型的影响不同）
  PENALTY_MAX  = 可配置上限（如最高扣 15 分，避免一条负面直接踢出列表）

最终排序分 = 基础匹配度 − feedback_penalty
```

**为什么是「软降权」而非「硬排除」**：负面反馈是**用户个人的主观经验**（「这家供应商的料我们没用过」并不代表材料不行）。硬排除会让系统把用户的主观偏见固化成规则，越用越窄。软降权保留材料在列表中的可见性，同时让排序反映历史经验——**用户可以推翻系统，但系统会记得用户的偏好**。

### 5.3 关于「语义理解」的边界建议（沿用 v0.1）

**建议不要追求让系统「听懂」自由表达，而是引导用户说出结构化信息。**

理由：本地小模型（bge 是 embedding 模型，不是生成模型，本身不具备推理能力）语义理解能力有限。让用户随便说，然后用规则硬猜，会导致：

- 抽错约束 → 推荐错误材料（**在材料选型场景，这个代价很高**）
- 抽漏约束 → 漏掉关键过滤条件

因此设计上做两件事：

1. **词典 + 正则优先**：零件类型、工艺、温度这些关键约束用领域词典精确匹配，不用模型猜
2. **回显确认**：抽取结果必须以标签形式让用户确认或修改后才能出结果

**语义向量只用在它擅长的地方**：在硬约束过滤后的候选集内，做「场景描述 ↔ 材料应用场景/特性描述」的相似度排序。这是 embedding 模型最可靠的应用方式。

> **v0.2 补充**：C1 的失败理由拆解同样遵循这一边界——**拆解结果只作为「反馈标签」记录，不直接改写推荐规则**，避免模型误解被放大成错误的排序。

### 5.4 术语与别名映射（v0.2：初版由 AI 生成）

为了让「保险丝座」「熔断器底座」「保险丝盒」「fuse holder」都能召回，需维护术语映射表（`term_alias`）。**v0.1 时这是需客户投入的关键数据资产；v0.2 已确认初版按常规使用习惯由 AI 生成**，后续用户在使用中持续补充（结合 C1 的需求缺口报告，指哪补哪）。

```
术语映射表（term_alias）
┌─────────────────┬──────────────────────┬──────────────┐
│ 标准术语          │ 同义表述               │ 类型          │
├─────────────────┼──────────────────────┼──────────────┤
│ 保险丝座         │ 熔断器底座/保险丝盒      │ 零件类型      │
│ 注塑             │ 注射成型/射出成型        │ 工艺          │
│ 长期使用温度上限  │ 连续使用温度/耐温        │ 参数          │
└─────────────────┴──────────────────────┴──────────────┘
```

| -------- | ------------------------------------------------------------------------- |
| 性能     | 检索响应 <500ms；推荐响应 <2s（含向量计算）；200 条数据规模下无压力         |
| 并发     | **单用户，无并发要求**（较 v0.1 从 10-30 人下调）                          |
| 部署     | **本机运行，无需联网、无需 Docker**；可选 PyInstaller 打包为单文件 exe      |
| 硬件     | 4 核 8G 内存起步（bge-small 约需 1GB）；无需 GPU                          |
| 数据安全 | 数据即本机 SQLite 单文件；建议**每日自动备份副本** + 定期手动导出材料包      |
| 可用性   | 本地进程，无对外服务；允许随用户开关机                                       |
| 兼容性   | Chrome / Edge 最新版；分辨率 1366×768 起                                   |
| 可维护性 | 材料分类体系、术语词典、**推荐权重与降权阈值**均**配置化**，不写死在代码里   |
| 审计     | 本地操作日志，记录时间与操作类型（单机单人，不记录「谁」）                    |
| **隐私** | **任务、待选备注、回评理由属个人数据，E1 导出默认不含**（可选包含）          |
| **可迁移** | 存储层抽象（Repository），DB 可换（SQLite↔PostgreSQL）而业务逻辑不变      |

### 7.2 关键风险（v0.2 更新）

| 风险                         | 影响                                                          | 应对                                                                                             |
| ---------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| **数据录入工作量被低估**     | 最大风险。200 条 × 每条约 30 字段 = 6000 数据点                | **一期已确认由 AI 搜集首批 50 条并建库**；人工只做抽检校对，从源头降本                            |
| 术语词典不全导致召回失败     | 「保险丝座」查不到 → 用户认为系统没用                          | 初版 AI 生成；结合 C1 需求缺口报告持续补充；提供「未命中反馈」入口                                  |
| 推荐结果不被信任             | 工程师宁愿问人                                                | 匹配度分数可拆解 + 参数标注来源 + **回评通道让用户能纠正系统**                                     |
| **回评数据量不足**（新增）   | 降权阈值达不到，反馈闭环形同虚设                              | 单机场景改为**提示优先、降权为辅**；阈值可下调至 1 并允许用户手动确认                              |
| **负面反馈误伤**（新增）     | 单次主观差评导致好材料被埋没                                  | **单条不降权**；软降权 + 可在设置中编辑/清空自己的反馈                                             |
| **跨机器分享 ID 冲突**（新增） | 两台电脑的自增 id 重复，导入后数据错乱                        | 引入**全局 uid（UUID）**作为去重键（见 4.5）；无 uuid 时按「名称+简称」兜底                        |
| **单机数据丢失**（新增）     | 硬盘故障 = 全部积累归零                                       | 每日自动备份 + 定期导出材料包（导出功能同时充当冷备份手段）                                        |
| 需求蔓延到「全量材料库」     | 工期失控                                                      | 严守 1.5 一期范围，Excel 批量导入、图谱推理明确推二期                                              |
| 本地模型效果不达预期         | 语义排序不准                                                  | 用规则权重兜底；语义分只占 25%；调整权重即可改善，无需换模型                                        |

## 10. 附录：与原始设想的差异说明（v0.2 更新）

| 原始设想                    | 本方案                                                            | 理由                                                        |
| --------------------------- | ----------------------------------------------------------------- | ----------------------------------------------------------- |
| 「建立一个材料库」          | 定位为「材料选型决策辅助系统」→ v0.2 升级为「个人选型工作台」      | 材料库是手段，解决「问人」痛点才是目的                      |
| 「知识图谱 + 语义理解推荐」 | 四段式混合推荐（规则过滤 + 向量排序 + 模板解释）                  | 200 条数据规模下图谱过度设计；硬约束过滤保证安全性          |
| 「智能推荐」隐含依赖大模型  | 一期用本地 embedding 模型（bge-small，100MB，CPU 可跑）+ 模板生成 | 满足「不允许外接大模型」约束，无需 GPU，零编造风险          |
| 未提及技术栈                | 建议 Python（FastAPI）而非 Go                                     | 语义模型生态 + SQL 聚合能力是决定性因素（详见 1.4）         |
| 未提及数据库                | **单机场景改为 SQLite**（v0.1 曾建议 PostgreSQL）                 | 多用户并发论据不成立；单文件易备份/分享，Windows 部署摩擦最小 |
| 未提及数据可信度            | 增加「数据来源 + 更新日期 + 认证信息」字段                        | 工程师不会使用无出处参数                                    |
| 未提及范围边界              | 明确列出「一期不做」清单                                          | 防止范围蔓延                                                |
| **未提及选型过程**（v0.2） | **新增选型任务 + 待选清单**                                       | 一次选材从「弹一次结果」变成「可回溯的工作线程」            |
| **未提及结果评价**（v0.2） | **新增回评 + 失败理由语义入库 + 软降权**                          | 让推荐质量可度量、可纠偏，指标第一次有真实数据源            |
| **未提及数据分享**（v0.2） | **新增导出 + 导入（uid 去重）**                                   | 突破「一个人一台电脑」，让个人积累可被同事复用              |
| **原设想的三级权限**（v0.2） | **移除**                                                         | 单机单人部署，权限与审核无意义                              |
