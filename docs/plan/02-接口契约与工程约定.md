### 3.1 统一响应与错误

- **成功**：直接返回业务对象（不包 envelope），与原型 `04-字段与接口映射` 的 `{ total, items }` 等形状一致。
- **失败**：HTTP 4xx/5xx + body `{"error": {"code": "<MACHINE_CODE>", "message": "<中文可读>"}}`。
- 错误码枚举：`NOT_FOUND` `VALIDATION_ERROR` `CONFLICT` `IMPORT_REJECTED` `INTERNAL`。
- 空值一律 `null`，**禁止空字符串**；时间一律 ISO 8601 带时区 `+08:00`。

### 4.6 补充冻结约定（多 Agent 交叉一致性关键）

**(a) 材料包校验和算法（E1 生成 / E2 校验必须完全一致）**

```python
import hashlib, json
def pack_checksum(materials: list[dict]) -> str:
    canonical = json.dumps(materials, ensure_ascii=False, sort_keys=True, separators=(",", ":"))
    return "sha256:" + hashlib.sha256(canonical.encode("utf-8")).hexdigest()
```
- 校验对象**仅** `materials` 数组；`checksum` 字段自身不参与计算。
- 前端不做校验和计算（只展示后端结论），避免三处实现漂移。

**(b) 支撑表 DDL（PRD 未给出，由架构师定义，其他模块只依赖表名与列名）**

```sql
CREATE TABLE category (            -- PRD 只提到 category(id)，此处补全
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name VARCHAR(100) NOT NULL,
    parent_id INTEGER REFERENCES category(id),
    sort_order INTEGER DEFAULT 0,
    created_at TIMESTAMP
);
CREATE TABLE operation_log (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    at TIMESTAMP NOT NULL,          -- 时间
    action VARCHAR(50) NOT NULL,    -- 新增材料 / 编辑材料 / 归档 / 导入 / 导出 / 回评 ...
    target VARCHAR(200),            -- 对象描述（材料名 / 任务名 / 文件名）
    detail TEXT                     -- JSON
);
CREATE TABLE settings_kv (          -- 权重 / 降权阈值 / 备份配置等配置化项
    key VARCHAR(100) PRIMARY KEY,
    value TEXT NOT NULL,            -- JSON
    updated_at TIMESTAMP
);
CREATE TABLE import_staging (       -- E2 两段式导入：parse 落暂存，commit 才写库
    token VARCHAR(64) PRIMARY KEY,
    payload TEXT NOT NULL,          -- 规范化后的材料包 JSON
    created_at TIMESTAMP
);
CREATE TABLE app_meta (key VARCHAR(100) PRIMARY KEY, value TEXT);  -- 版本号 / 最后备份时间
```
- `material_fts`（FTS5）必须建 `INSERT/UPDATE/DELETE` 三个同步触发器；
  `tokenize='trigram'` 若当前 SQLite 不支持，**自动回退** `unicode61` 并在启动日志告警。
- 所有时间戳统一 `datetime('now','+8 hours')` 语义或 Python 侧写入 `+08:00` ISO 字符串，二者选一，由架构师在 `db/connection.py` 统一提供 `now_iso()`，**其他模块禁止自行取时间**。

## 5. 推荐算法契约（PRD §5.1 / §5.2 落地口径）

1. **约束抽取**：词典（`term_alias` + 内置零件类型/工艺词典）+ 正则数值提取（`(\d+)\s*(°C|℃|度)` → temp_limit）；
   置信度 = 命中约束项数 / 期望项数（部分命中 0.5）。全部未命中 → `degraded=true`。
2. **硬约束过滤**（SQL WHERE，绝不返回不满足项）：`service_temp_limit >= temp_limit` 且 `molding_process` 含 `process` 且 `archived=0`。
   为空 → 放宽：温度 -10 后重试，`relaxed` 记录放宽项；仍为空 → `results=[]` + `degraded=true`。
3. **加权打分**（权重可配，默认如下，自动归一化）：
   `temp 0.30 / semantic 0.25 / cost 0.20 / mechanics 0.15 / process 0.10`，再减 `feedback_penalty`。
   - `temp`：裕度 = limit − 需求；裕度 0~20% 得满分，过大线性扣分（避免过度设计）。
   - `semantic`：候选集内 `cosine(n-gram(user_text), 材料场景+特性文本)`。
   - `cost`：价格落在用户预算区间得满分；用户未提成本 → 中性 0.6 基线。
   - `mechanics`：按 `part_type` 推断（电气件→阻燃/绝缘加权；承力件→拉伸强度加权；外观件→表面特性加权）。
   - `process`：完全匹配 1.0，需后处理 0.6，需改性 0.3。
   - `feedback_penalty`：`Σ_d min(hits_d/THRESHOLD,1)*DIM_WEIGHT[d]*PENALTY_MAX`，`THRESHOLD=2`、`PENALTY_MAX=15`；单条不计。
   - `score < 60` 不进入结果列表。
4. **解释生成**：**模板 + 槽位填充，禁止 LLM 自由生成**；`reason` 中所有数值必须来自库中字段。
   `key_params` 顺序固定：拉伸强度 → 长期耐温上限 → 参考价 → 密度 → 推荐工艺。
   `alternatives` = 第 2~3 名 + 代价说明（成本/工艺/耐温差异）。

## 6. Git 规范（PRD「严格遵守 Git 规范」落地）

### 6.1 分支模型（简化 GitFlow）

| 分支 | 用途 |
| --- | --- |
| `main` | 稳定可交付；只接受来自 `dev` 的合并；每个里程碑打 tag |
| `dev` | 集成分支；各功能分支合入目标 |
| `feat/<模块>` | 功能开发：`feat/backend-materials`、`feat/frontend-workbench` |
| `data/<模块>` | 数据构建：`data/seed-50-materials` |
| `test/<模块>` | 验收与测试：`test/acceptance-suite` |
| `docs/<模块>` | 文档：`docs/plan` |
| `fix/<问题>` | 缺陷修复 |

- 每位专家**在自己的分支上工作**，完成后合入 `dev`；里程碑结束时 `dev` → `main` 并打 tag（`v0.1.0-m1` 起）。
- 分支命名小写 + 连字符；禁止在 `main` 直接提交。

### 6.2 提交信息（Conventional Commits）

```
<type>(<scope>): <subject>

<body 可选：为什么这么改>
<footer 可选：Refs #任务号 / BREAKING CHANGE>
```

`type ∈ {feat, fix, docs, style, refactor, test, chore, data, build}`；`scope` = 模块（materials/recommend/tasks/ui/tokens/git…）。
示例：`feat(recommend): 实现硬约束过滤与加权排序`

### 6.3 里程碑 Tag

`v0.1.0-m0`(规划) → `v0.2.0-m1`(框架) → `v0.3.0-m2`(数据) → `v0.4.0-m3`(后端) → `v0.5.0-m4`(前端) → `v1.0.0`(验收交付)
