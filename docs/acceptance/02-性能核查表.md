## 2. 方法学：为什么必须重建性能基线

原有 `backend/tests/test_api_settings.py::test_perf_*` 三条用例运行在 **受控种子 8 条**上，实测**单次耗时 < 5ms**（`pytest --durations=0` 显示 8 项耗时均 < 0.005s），且其 `-vv` 输出中 `setup` 一项即占 0.09s。

**结论：这三条用例可以证明「逻辑不存在明显性能缺陷」，但不足以支撑 §8.2 的「200 条规模」达标结论**——用 8 条数据宣称 200 条规模达标属于口径不符。因此新增 `backend/tests/test_perf_scale.py`，构造**真实 200 条数据集**并复测。

新增基线具备三项防伪设计：

| 设计 | 作用 |
| --- | --- |
| 数据集守卫 `test_scale_dataset_actually_200` 断言 `total == 200` | 防止「空库/少量数据跑出好看数字」的假达标 |
| 独立临时库 + fixture 结束后还原 `MATSELECT_DB` | 不污染 conftest 的 session 临时库（否则会破坏 `材料总数 == 8` 类断言） |
| 按 **p95** 判定 + 同时输出 p50/max | 避免单次抖动误判，且不隐藏最差值 |

## 5. 判定与**口径覆盖度**（关键限定，不得省略）

| 口径 | 后端接口层 | 前端真实渲染 | 综合判定 |
| --- | --- | --- | --- |
| 检索 < 500ms | **已实测达标**（200 条，p95 4.6ms） | 未测（检索交互含前端渲染） | 后端达标；端到端待补 |
| 推荐 < 2s | **已实测达标**（200 条，p95 8.0ms） | 未测（结论面板渲染） | 后端达标；端到端待补 |
| 材料库首屏 < 1s | 仅覆盖**数据拉取**（p95 5.0ms） | **未测** | ⚠️ **口径未闭合** |

> **重要限定**：`TestClient` 为进程内直调，**不含真实 HTTP 传输、不含前端渲染、不含浏览器主线程**。因此上表三行只能证明「后端服务耗时远低于阈值」，**不能**单独作为 §8.2「首屏 < 1s（卡片视图）」的完整证据。
> 「首屏」的真实口径是用户可见首帧，需用浏览器 Performance API（`navigation` + `first-contentful-paint`/`largest-contentful-paint`）在 1366 视口、200 条数据下测量。该项已登记为 04 号报告整改项 **A1（P0）**，本核查表**不将其判定为已达标**。

## 6. 性能风险提示

| 编号 | 风险 | 依据 | 影响 |
| --- | --- | --- | --- |
| P-1 | 200 条规模余量极大（百倍级），但**未覆盖 1000+ 条**规模 | 口径仅要求 200 条 | 一期无风险；二期扩容需重测 |
| P-2 | 推荐耗时随「约束放宽（relax）」轮次与候选集增长 | `recommend/run` 含 relax 分支 | 需在 04 号整改项跟踪 |
| P-3 | 全量列表 `GET /api/materials` 未测**无分页**极端场景 | 前端卡片视图默认分页 | 低 |
| P-4 | 导入 200 条以上时的解析/落库耗时未纳入口径 | E2 两段式导入 | 一期不阻塞，登记观察 |
